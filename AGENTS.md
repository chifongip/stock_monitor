# Repository Guidelines

## Project Structure & Module Organization

- `terminal-stock-alert.js` is the Node.js CLI entry point. It fetches Hong Kong
  stock data, renders the terminal table, handles commands, and persists state.
- `stocks.json` is the runtime watchlist and alert configuration. Preserve its
  JSON shape when changing defaults or persistence behavior.
- `asset/` contains application assets, including `asset/icon.png`.
- `dist/` and `build/` are generated by the packaging workflow; do not edit or
  commit their contents unless intentionally preparing a distributable release.

Keep feature changes close to the relevant CLI function. If the script grows
substantially, split reusable logic into clearly named CommonJS modules.

## Build, Test, and Development Commands

- `npm install` installs the declared dependencies.
- `npm start` runs the CLI locally (`node terminal-stock-alert.js`). Use this to
  check commands such as `a 00700`, `t 00700 500`, `ua 00700`, and `s`.
- `npm run build` packages Linux, macOS, and Windows executables with `pkg`.

There is currently no `npm test`, linter, or formatter script. Before opening a
change, run `npm start` and manually verify the changed flow, configuration
write-back, terminal rendering, and errors from unavailable market data.

## Coding Style & Naming Conventions

Use JavaScript with CommonJS (`require`) and four-space indentation, matching
`terminal-stock-alert.js`. Use `camelCase` for variables and functions, and
`UPPER_SNAKE_CASE` for module-level constants such as `CONFIG_FILE`. Keep stock
codes as zero-padded strings (for example, `'00700'`), not numbers. Prefer
small guard clauses and explicit error handling around network and file I/O.

When adding a runtime package, update `package.json`; also update the `pkg`
asset configuration if the package needs files bundled into the executable.

## Commit & Pull Request Guidelines

Recent commits use short, imperative release-oriented summaries, for example
`release v0.0.3, add sorting method`. Follow that style: state the primary
change in one concise subject line.

Pull requests should describe behavioral changes, list the commands run, and
note configuration or packaging impact. Include a terminal screenshot or sample
output for table or command-interface changes, and link the relevant issue when
one exists.
